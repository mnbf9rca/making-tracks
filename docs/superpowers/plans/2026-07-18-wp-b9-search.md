# WP-B9 — Search: name lookup + geocoding, LOCAL (privacy)

**Status:** design (opus). Adversarial-gate → PR to `develop`, `sourcery-review`. Pipeline → `develop`,
app → `ios`. Thread `p2p/fable__opus`. Spec §5.3/B9 (#20). Depends on B3 (tile client, built).

## Why

Spec: *"name lookup over region place data + geocoding to jump the map — 'Edinburgh next month' must have
an entry point that isn't panning across the planet. Simple is fine; absent is not."* The design tension:
the app only holds the **current viewport's** tiles (+ visited/saved snapshots), so full-region name
search needs a **published index** — and the privacy-clean way is a **local** search (queries never leave
the device).

## Grounded facts (recon: app `origin/ios`; contracts/pipeline `develop`; cited)

- **Search is entirely GREENFIELD** — no search screen, no geocoder, no `CLGeocoder`, no search index
  (grep-empty on both the app and a published-artifact schema).
- **Local name availability is a SUBSET only:** `place_snapshots.name` (visited/saved places) +
  `lists.name` + the **current viewport's loaded tiles**. There is **no** local corpus of the region's
  place names → full-region search needs a new published artifact.
- **The geocoding gazetteer is DESIGNED (#177 WP-RM-P) but NOT BUILT [gate — correction].** #177's
  `WP-RM-P` designs an OSM `boundary=administrative` **sub-extractor** (names + centroids), but it is
  unmerged **and** requires a **new OSM tag filter** — `osm_candidate_tags.json` today whitelists only
  `historic`/`tourism`/`memorial`/`man_made`, **no `place=`/`admin_level`/`boundary`** — so "Edinburgh"
  (a city / admin relation) is currently extracted by **nothing**. So geocoding-by-zone **BLOCKS on
  WP-RM-P shipping**; **v1 = place-name search over the published places**, geocoding-by-zone follows
  (sequenced after WP-RM-P). *(The earlier draft mis-stated this as a grounded fact.)*
- **Rob's ruling (#177): packs bundle "everything."** The search index **joins the pack**, but — like the
  other sidecars — it is listed in the **versioned PACK-DESCRIPTOR file, NOT the frozen manifest**
  (`manifest.schema` is `const 1` + `additionalProperties:false`; sidecars can't ride it, region-model §6).
- **#167 (merged): hide is MAP-ONLY** — a hidden place still exists and is *findable via search, marked
  hidden with Unhide*. Category-layer toggles are a *map* filter, not a search filter.

## 1. The published SEARCH INDEX (D1 — new contract)

- **A per-region `search-index`** (new versioned schema, `min_reader_version`, `additionalProperties:false`):
  entries `{name, alt_names[], kind (place | zone), place_id (null for zone entries), lat, lon, tier,
  category}`. **Corpus = the SHIPPED places [gate — pin to `final_places`]:** the index is built from the
  **post-overflow/exclusion `final_places`** the tiles actually carry (not a broader corpus) — else a
  searchable `place_id` exists in **no tile** and its card is permanently unresolvable (§3). Zone entries
  (geocoding) come from WP-RM-P when it ships.
- **SHARDED for delta [gate — a monolithic per-region file is NOT delta-capable].** A single index file
  changes on essentially every publish (re-scoring/reconcile) → a full re-download, the opposite of
  incremental (and #177 §7 warns against monolithic per-area blobs). So the index is **sharded**
  (prefix- or z10-tile-scoped shards, each independently `{sha, bytes}`-listed in the **pack-descriptor**)
  → only content-changed shards re-download, deltaing like tiles.
- **Delivery + size [gate — the region can be ~600k places]:**
  - **In the pack** (offline users): the sharded index rides the pack, listed in the **pack-descriptor**
    (not the manifest), delta per shard.
  - **Online (no pack):** a **tier-gated compact** index (notable subset T1–T2 + zone names) fetched
    whole — small. *(NOT prefix-sharded-on-demand: fetching a shard by typed prefix would egress the
    query prefix to the CDN, breaking §2's "no query leaves the device" — so the online index is a whole
    compact download, never per-keystroke shard fetches.)*
  - Untrusted (§5.5): the index is size-capped, `name` SAFE_TEXT + plain-text, `place_id` pattern-checked,
    lat/lon bounded, `kind` enum. Written-last/atomic; versioned.

## 2. Local search — queries NEVER leave the device (D2 — the privacy property)

- **Search runs entirely LOCALLY over the downloaded index** — a prefix + light fuzzy match (folded/
  diacritic-insensitive; matches `name` + `alt_names`), ranked by `(tier, match-quality)`. **No search
  query ever hits the network** (search intent + location is highly sensitive; this is a first-class
  privacy property — state it, and it falls out of the static index). GRDB FTS5 or an in-memory index
  over the loaded search-index file.
- **No third-party geocoder by default.** "Jump to Edinburgh" is served by the index's **zone/admin
  entries** (WP-RM gazetteer), not Apple's `CLGeocoder` (which would send the query + IP to Apple).
  `CLGeocoder` is at most a **disclosed, opt-in fallback** for a miss — flag the privacy tradeoff; v1
  recommend index-only (honest "no result" beats a silent third-party query).

## 3. Search UX (D3)

- A **Search screen** (a tab / a search field reachable from the map). Type → **live local results**
  (places with their category icon + a "zone/place" hint). Tap a **zone** → recenter the map there.
- **Tap a place → jump, then RESOLVE the card [gate — the data path can't open a card synchronously].**
  The card resolves only from **loaded-viewport tiles or a local snapshot** (`PlaceResolver` → no
  fetch-by-place-id); a searched place is off-viewport and un-visited → `.unavailable` until its tile
  loads. So the flow is: **jump the camera to `lat/lon` → await the covering z10 tile's load → resolve
  the full card from it**, showing a brief **loading state** meanwhile. Because the corpus is pinned to
  `final_places` (§1), the covering tile **always contains the id** (no permanent miss). *(The index
  entry alone can't build the card — it lacks blurb/photo/sources; the card must come from the tile.)*
- **Empty/short-query** shows nothing (or recent); a miss shows an honest "no match in <region>".
  Accessible (Dynamic Type, VoiceOver — #163): the result list is the primary accessible path.
- **Recent searches — OFF by default, or a protected local store [gate — privacy].** A persisted query
  history *is* the sensitive "search intent + location" signal §2 keeps off the network, so persisting it
  naively would sweep it into iCloud/Finder backups (off-device). If shipped: **exclude the store from
  backup** (`isExcludedFromBackup`) + a first-unlock data-protection class + a length/TTL cap + a
  **clear-history** control. **Recommend default-off** for v1.

## 4. Interplay — hidden places + category toggles (D4)

- **Hidden places APPEAR in search, marked hidden, with Unhide** (#167 map-only ruling — hide affects the
  discovery *map*, not findability). So search is the re-find path Rob's map-only ruling relies on.
  **[gate — the card Unhide is NOT built yet].** What merged (#175 = **WP-HIDE**) is the hidden *state +
  filter* (`hidden_places`, `setHidden`/`unhide`, the map filter); the **card's Unhide button is
  WP-HIDE-UX**, which is **unbuilt** (`PinState.hidden` + `unhide()` plumbing exist, but no card control
  invokes them). So B9 either **sequences after WP-HIDE-UX** or **scopes the card Unhide into WP-B9-B**
  (the plumbing exists; add the button in the hidden state). Don't assume it's already there.
- **Category-layer toggles do NOT filter search** — they are a *map* declutter (a style-layer filter,
  #170), not a statement about findability. Search is global across categories. (A search-side category
  facet is a possible later refinement, not v1.)

## Gate & acceptance

- **Adversarial gate (done): 3 critics + verify, 11 raised, 7 survived, all folded.** The gate caught a
  rushed draft:
  - **"sha-listed in the manifest" was impossible** — the manifest is frozen (`const 1`,
    `additionalProperties:false`); the index rides the **pack-descriptor** (§1). *(Same error was in WP-RM
    #177 + offline.md — corrected there too.)*
  - **Geocoding depended on a phantom/unbuilt extraction** — WP-RM-P (OSM boundaries) is designed in #177,
    not built, and needs a new tag filter; v1 = place-name search, geo follows (§Grounded/flags).
  - **A monolithic index isn't delta-capable** — sharded it (§1).
  - **Jump→card can't resolve synchronously** — jump → await covering tile → resolve, corpus pinned to
    `final_places` (§3).
  - **The card Unhide doesn't exist yet** (it's WP-HIDE-UX) — corrected (§4).
  - **Recent searches** at-rest exposure — default-off/protected (§3).
  The local-search privacy spine + the published-index architecture survived; the folds were the delivery
  container, the geo dependency honesty, and the app-side resolution/sequencing.
- PR → `develop`, `sourcery-review` only, report `p2p/fable__opus`. No self-merge; fable reviews; `main`
  is Rob's.
