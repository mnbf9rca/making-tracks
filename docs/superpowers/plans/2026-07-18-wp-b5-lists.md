# WP-B5 — Lists (local-only; sharing is a seam, not built)

**Status:** design (opus). Adversarial-gate → PR to `develop`, `sourcery-review`. App → `ios`. Thread
`p2p/fable__opus`. Spec §3.1/§3.2/§5.4/B5 (#…). Depends on B4 (card, built). **Sharing is explicitly
out of scope until accounts exist (privacy.md); design the seam, not the sharing.**

## Why

"Bookmarks are a list" (§3.2): the app ships one system list **"Want to go"** (the quick-save tap adds
to it); custom lists ("Date nights", "KL trip") are the **same mechanism**. B5 is the Lists UI —
create/manage lists, add/remove places, and view a list as a checklist or on the map — all **local**,
no server. It also fixes the `saved`-derivation pre-condition the card overhaul flagged.

## Grounded facts (recon: app `origin/ios`; cited)

- **Data model is BUILT** (`Migrations.swift`): `lists {id, name, is_system, created_at}` (seeded
  "Want to go", `is_system=1`); `list_items {list_id (cascade), place_id, added_at, PK(list_id,
  place_id)}`; models `PlaceList`/`ListItem`. **Derivations built:** `listProgress(listID) → (visited,
  total)`, `viewportState` (pin state).
- **`saved` = membership in ANY list** (`viewportState`, `Derivations.swift:81`, no `list_id` filter) —
  the load-bearing bug the card gate flagged: once a place is in a **custom** list but not "Want to go",
  the pin reads saved yet the card's Save (`removeFromList("Want to go")`) is a no-op → can't clear.
- **No Lists UI exists** — only the models + derivations. The place card's Save = add to "Want to go"
  (WP-CARD); the card's **list-membership chips** (WP-CARD §0.4) are the display seam B5 fills.
- **Sharing is a v2 seam already captured (§9 amendment):** per-list visibility (private / public link),
  permission tiers **viewer / contributor / editor**, `list_items.added_by` arrives **by migration with
  sharing** — **v1 schema needs no change**. Accounts (data-minimized) + CloudKit sync are v2, Rob-gated.
- **Seen is per-PLACE, not per-list** (§3.1): a list renders visit-*progress* (visit timestamps), never
  a per-list seen flag.

## 1. Lists screen (D1)

- **Lists is a menu-chip entry → a sheet over the map** (binds to the ratified #176 IA: full-bleed map,
  no tab bar, sheets over the map — **NOT a tab or a standalone screen**). The Lists sheet shows the
  user's lists, each with its **`listProgress`** ("3 of 12 visited") and item count. **"Want to go" is
  system-special** (pinned first; **cannot be deleted or renamed** — `is_system=1`); custom lists can be
  **created, renamed, deleted** (delete cascades `list_items`, per the schema — confirm the
  destructive-delete confirm).
- **Create** a list (name, SAFE_TEXT + length-capped like other user strings). Local-only, no network.

## 2. List detail — item view + map view (D2)

- **Item view (the "gift problem" presentation, §3.1):** leads with **progress** — "you've been to 3 of
  these · 7 to go" — the places as a checklist, **visited items checked** (from the per-place visit
  state, not a per-list flag). Never framed as "30% consumed" (§3.1 anti-goal). Tap a row → the place
  card. Remove-from-list (swipe/edit).
- **Hidden members STAY in the list, with Unhide [gate — Rob's ruling, was wholly absent].** Hide is a
  **map-triage state on the *discovery* map** (#170/#175), not a statement about the user's own
  curation. So a hidden place that is **on a list remains fully present in that list**: the **item view
  shows the row** (marked hidden) with an **Unhide affordance**, and — because a list is the user's own
  curation, not the discovery firehose — **the list MAP shows hidden members too** (they do NOT vanish
  from their own list's map). This is the opposite of the discovery map's `showHidden:false` declutter,
  and is deliberate: you curated it, so you see it. The **Unhide control is WP-HIDE-UX** (`unhide()`
  plumbing exists; the button does not) — **WP-B5 interlocks with WP-HIDE-UX** (sequence after it, or scope
  the list-row/item-view Unhide into WP-B5-a), same as B9's card-Unhide interlock. *(If Rob prefers the
  list map to also honor hide, that is a one-line flag flip — but it contradicts "a list is your
  curation"; recommend list-map-shows-hidden.)*
- **Map view (§3.2):** the list's places on the **map**, **fading visited pins exactly like discovery**.
  **It reuses B2's render/decorate layer** (`PinLayers`, `pinAppearance`, `viewportState` — which take an
  arbitrary `[(MapPlace, PinState)]`) but **NOT B2's feature feed** [gate — the list map has no data
  source as first-drafted]. B2's only `[MapPlace]` producer is `places(inViewport:zoom:)` —
  **viewport-driven**, so a list like "KL trip" viewed from home would render **empty**. So WP-B5-a must
  build **a new snapshot-backed feed**: a batch `[place_id] → [MapPlace]` query over `place_snapshots`
  (which already stores lat/lon/tier, populated by `snapshotIfNeeded` on add-to-list — the only accessor
  today is the single-key `snapshot(for:)`, so the batch query is new) **plus a camera-fit-to-list** (also
  unbuilt). Not "the same map, scoped" — the render substrate is reused, the geometry feed is new.
  - **List-map is list-EXCLUSIVE:** it renders the list's `place_id`s only (from the snapshot feed), **not
    overlaid on the discovery viewport feed** — so no dedupe/precedence question arises. Coordinates come
    from `place_snapshots` and may be **stale** (captured at add-time); accepted until the place's next
    card resolve refreshes the snapshot. Hidden members included (above); visited members fade.
  - **The "Fresh snow / My tracks" toggle is B8 scope [gate — no silent scope].** That visit-history
    toggle (§17/§3.2) is **B8, unbuilt**. Either **WP-B5-a builds the toggle control here** (and says so
    explicitly — **B8 then inherits it**) or B5 ships the list map **without** it and **declares B8 as a
    dependency**. Recommend: **WP-B5-a builds the control** (it is a small view over the same visit state
    the item view already reads) so the list map is complete; flag for Rob/fable. Do not leave it implied.
- **These render progress the SAME way a shared list will (§3.1)** — the item/map views are the
  share-ready presentation; sharing just changes *who* sees them (§5).

## 3. Add / remove a place to a list (D3)

- From the **place card**: **Save** = the quick-add to "Want to go" (WP-CARD, built); **"Add to
  list…"** opens a picker of the user's lists (+ "New list…") to add to a **custom** list. Remove from a
  list from the card or the list's item view. The card's **list-membership chips** (WP-CARD §0.4) show
  which **custom** lists the place is in and become the tap target.
- Idempotent (the `PK(list_id, place_id)` makes re-add a no-op); local-only.

## 4. Fix the `saved`-derivation (D4) — the B5 pre-condition [gate]

- **Narrow `saved` to "in the 'Want to go' list", NOT "in any list".** Today `viewportState` derives
  `saved` from membership in **any** `list_items` row; once B5 ships custom lists, a place in only a
  custom list would read `saved=true` while the Save button's `removeFromList("Want to go")` no-ops
  (can't clear) — the latent bug the card overhaul flagged. **B5 owns the fix:** `saved` (the pin's
  **bookmark badge**) = membership in the **Want-to-go** list specifically; **custom-list membership is
  a separate concept** (the card chips, §3). Change: `viewportState`'s `saved` set is `SELECT DISTINCT
  place_id FROM list_items` with **no `list_id` filter** (`Derivations.swift:84`) → add `WHERE list_id =
  wantToGoListID` (reuse the existing `wantToGoListID()`, `Interactions.swift:142` — don't re-resolve).
  (This keeps the WP-CARD Save button coherent.)
- **The test must have TEETH — and go in the RIGHT layer [gate].** The existing "pin-matrix tests" do
  **not** exercise this: `PinMatrixTests` is a pure `PinState → PinAppearance` mapping table that never
  touches the DB, and every `saved` row in `CoreLoopControllerTests` is set via `setSaved` → which routes
  through `wantToGoListID` — so **every existing test stays green even if the `list_id` filter is removed**
  (the exact "neuter the fix → nothing goes red" failure this project forbids). So B5 adds a **new
  discriminating derivation test** (in the Derivations/CoreLoop layer, not `PinMatrixTests`): a place in a
  **custom list only** (`list_id ≠` the Want-to-go id) must read **`viewportState([p])[p].saved == false`**,
  and a place in Want-to-go must read **`saved == true`**. **Neutering the `list_id = wantToGoListID`
  filter must turn this test red** — that is the gate artifact.

## 5. Sharing SEAM — designed, NOT built (D5)

- **The list is the shareable unit; v1 builds it share-READY, ships zero sharing.** Per §9 (captured):
  a list will gain per-list **visibility** (private / public link) and **permission tiers** (viewer /
  contributor / editor); **`list_items.added_by` arrives by migration WITH sharing** — **v1 schema
  changes nothing** (the seam is that the model already suffices). Sharing needs **accounts**
  (data-minimized, v2) + server-mediated contributor/editor state — **all v2, Rob-gated, OUT of scope
  here.** B5 designs the local list so v2 sharing is additive: the item/map views already render as a
  shared list would (§2); no local-list decision blocks the v2 sharing design.
- **Shared-list progress is ALWAYS the viewer's own local visit state [pin — privacy].** Even when a list
  is shared, its progress ("3 of 12 visited") and pin-fade are computed from the **viewer's own** visits —
  **visits never travel** (privacy.md:52). A shared list conveys *which places*, never *who visited what*;
  two viewers of the same list see different progress, each their own. This is why §2's item/map views are
  already share-ready: they read local visit state, and that never changes.
- **Seam inventory (arrives-by-migration, nothing v1):** `list_items.added_by` (who added a place),
  per-list `visibility`, and `permission tier` all arrive **by migration with the v2 sharing build** — v1
  persists none of them and needs no schema change.
- **Privacy:** lists are **local user data** (like visits) — no server, no network, nothing leaves the
  device (privacy.md); iCloud device-backup scope like the rest of the DB. No sharing until accounts.

## Gate & acceptance

- **Adversarial gate (done): 3 critics + verify, 7 raised, 3 survived, all folded.** Survivors (all
  verified against the tree):
  - **The list Map view had no data source** (SEV-3) — B2's only `[MapPlace]` feed is viewport-driven, so
    a list viewed from elsewhere renders empty; folded a new `place_snapshots`-backed feed + camera-fit
    into §2/WP-B5-a, and dropped the "same map, scoped" framing.

    defect) — `PinMatrixTests` is a pure mapping table and all `CoreLoopControllerTests` `saved` rows go
    through Want-to-go, so neutering the `list_id` filter left everything green; folded a **new
    discriminating derivation test** (custom-list-only → `saved=false`) as the gate artifact into §4/WP-B5-b.
- **fable fallback review (2 MAJOR + 4, all folded):**
  - **Hidden places were wholly absent** (MAJOR, contradicts Rob's ruling) — hidden STAYS in lists with
    Unhide; the list map reused `showHidden:false` so a hidden member vanished from its own list. Folded:
    item view shows hidden rows + Unhide, **list map shows hidden members** (a list is the user's curation,
    hide is discovery-map triage), WP-HIDE-UX interlock stated (§2, flag 3).
  - **IA slip** (MAJOR, same as #178 pre-fold) — "a tab / Lists screen" → **menu-chip → sheet, #176** (§1).
  - **Fresh-snow toggle was silent B8 scope** — WP-B5-a now explicitly builds the toggle (B8 inherits);

  - **List-map exclusivity** pinned (list pins only, no discovery overlay; stale snapshot coords accepted

  - **Shared-list progress** = always the viewer's own local visits (visits never travel, privacy.md:52);
